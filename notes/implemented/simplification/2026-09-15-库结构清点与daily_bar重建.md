# 决策档案: 库结构清点与 daily_bar 改 WITHOUT ROWID

Status: implemented

## Problem

建表 DDL 全是 `CREATE TABLE/INDEX IF NOT EXISTS`，**只做加法**。一次跨版本重写之后，旧二进制留下的对象会永远躺在库里，既占空间又让"这张表还有人读吗"无法回答。开发库实测（2026-09-15，31MB）：

- 16 张 0 行废表（`moneyflow` / `news` / `top_list` / `agent_debate` / `trade_plan` 等，均为重写前旧版遗留）；
- 2 个与现役索引重复的索引：`idx_daily_bar_ts_code`（与主键 `(ts_code, trade_date)` 前缀重复，6.6MB）、`idx_daily_bar_trade_date`（与 `idx_bar_date` 同列重复，2.9MB）；
- `daily_bar` 用普通表，其主键要额外维护一棵 **10.0MB** 的索引，而表数据只有 6.8MB。

结果：31MB 的库里有 16MB 是历史遗留物，且没有任何机制提示它们的存在。

## Decision

1. **启动期清点 + `db audit` 子命令**（`internal/store/audit.go`）：把 `sqlite_master` 与代码内的现役清单（`SchemaTables` / `SchemaIndexes`）对一遍，报出遗留表、遗留索引、缺失表、以及 `daily_bar` 是否还是普通表。**只清点、不自动 DROP**——删表不可逆，交人拿清单决定。`sqlite_autoindex_*`（主键自动索引）排除在具名索引之外。
2. **`daily_bar` 改 `WITHOUT ROWID`**：本表是全库唯一的窄列复合主键表，主键即唯一访问路径，没有 `rowid` 消费方。WITHOUT ROWID 让主键 B 树就是表本身，省掉那棵 10MB 的独立索引。
3. **`db rebuild-bar`**：旧库需离线重建才能拿到空间（`WITHOUT ROWID` 无法在运行期改）。单事务内复制 → 行数核对 → 替换 + 重建索引；核对不过直接回滚，原表不动。
4. **`DeleteBatchedRows`**：原 `DeleteBatched` 走 `rowid IN (SELECT ...)` 子查询，在 WITHOUT ROWID 表上会直接报错。新增按主键元组（行值 IN 子查询）的分批删除；`RetentionRule` 增加 `PKCols` 字段声明该表的主键列，保留清理据此选删除方式。

## Alternatives considered

- **启动时自动 `DROP` 遗留表**：删表不可逆，误判一次就是数据丢失。改为只清点 + 非零退出，交人决定。
- **把遗留索引一并自动删掉**：同理。`db audit` 只点名。
- **`daily_bar` 拆成个股表 + 指数表**：指数与个股同形、同访问路径、代码不重叠，拆开只会多一张表多一套保留规则（ARCHITECTURE 已按"同形同窗口则不拆"判据合并）。
- **保留 `rowid`、改用 `DELETE ... LIMIT`**：modernc.org/sqlite 未开启 `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`，不支持该语法（这是原实现走 rowid 子查询的原因）。
- **一次性 `VACUUM` 回收空间**：长事务会锁库。沿用既有的 `incremental_vacuum`。

## Consequences

- 换来：库结构有了自检与自愈路径。开发库实测 **31MB → 15MB → 12MB**（清遗留物 + WITHOUT ROWID 重建），行数与 `integrity_check` 均无异常。
- 代价一：`daily_bar` 不再有 `rowid`。任何按 `rowid` 定位的新旧代码都会失败——已在 `DeleteBatchedRows` 注释与 `RetentionRules.PKCols` 写明。
- 代价二：`db rebuild-bar` 必须离线执行（重建期要 DROP 原表）。已在子命令文档与调用点说明。
- 遗留：清理动作本身仍需人工执行 SQL（`db audit` 只报告）。自动化删除属破坏性操作，刻意不做。
